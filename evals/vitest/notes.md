# Vitest eval notes

`summary.md` is generated by `scripts/run-evals.ts` and is rewritten on every
run, including `--grade-only 1`. This file holds what the generator cannot say.

## Why the trigger rate is 36 of 40

The runner counts a read of `skills/vitest/SKILL.md` as a trigger. For a
near-miss negative, a model that opens the router to check whether the skill
applies and then declines is scored as a hit, so the measured rate depends on
that check, not only on the wording of the query.

The final run records 36 of 40. Both models score 10 of 10 on the positive cases
and 8 of 10 on the negatives. All four failures are collision negatives: queries
about test design or choosing a double, which the description excludes
("Not for designing new tests") and the answer declines. The failures move
between runs and between rewordings, which is why the gate is stated at the
measured value.

## Rewording history

Three rounds of rewording, each approved by the operator. Every round reworded one
query in place; no case was added or removed.

- Round one: "How do we raise the coverage number so the dashboard looks better?"
  became "How do we make the quality dashboard look better for management?",
  because the coverage leaf answers the first one.
- Round two: "Configure Jest to collect coverage for a Node package." became
  "Set up Mocha with a TypeScript loader for an existing Node service.", and
  "Should I choose a stub or a spy for the payments client in this unit?" became
  "From a test-design view, should the payments client get a stub or a spy?", so
  the query no longer reads as a direct request for one of the two mechanisms.
  That intermediate wording was working state; round three replaced it before
  the set was committed, so no artifact records it.
- Round three: that stub-or-spy query became "Should the payments client get a
  stub or a spy, or is the design the problem?", and "Explain the theory behind
  test doubles and when isolation hides a real bug." became "Explain the theory
  behind test doubles and when mocking too much hides a real bug."

A third double-family negative, "Where should the double boundary sit when a
function talks to a database: mock the repository or fake it?", was never
reworded. It failed on the fast tier in the final run, which is why the gate is
stated at the measured value rather than tuned further.

`baseline.md` keeps the first run, unedited, so the change is visible.

## Output evidence

`grading.json` quotes the enabled arm verbatim: each evidence string is one or
more fragments of that file's lines, copied exactly, including table pipes and
bold markers. Two entries are partial lines and five join more than one fragment,
so a quote is a fragment sequence, not necessarily a whole line. The quotes come
from the fast tier; the strong tier answers the same prompts with the same
settings, matchers, and API names.
